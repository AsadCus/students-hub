# Students-Hub

School kiosk + admin app: student check-in/out, facility bookings, counselling questionnaires ("Ask Ms Vi") and equipment loans. Laravel 11 JSON API (`routes/api.php`, Sanctum bearer tokens, spatie/laravel-permission) plus a React SPA in `resources/js` (Vite, Redux Toolkit, PrimeReact, Tailwind 4). It is **not** Inertia: the SPA talks to the API over axios. MySQL locally, database queue.

All user-facing text is English.

## How a module is built ("master types")

Most data is a master type, listed in `config('constants.MASTER_TYPE_ARRAY')`. One type name drives everything:

- **Routes:** `routes/api.php` generates `/api/{type}` list/show/create/update/delete/import for every type.
- **Controller:** `MasterApiController` holds per-type branches (validation rules in `getRuleValidationByType`, special `store`/`update` logic). Rules live in `config('constants.MASTER_VALIDATION_ARRAY')`. Uniqueness that must ignore the record on update is added in the controller with `Rule::unique(...)->ignore($id)`.
- **Service:** `MasterService` maps type → model (`$modelMap`), builds list queries with filters (`getAll`) and delete cascades/guards (`delete`).
- **Permissions:** `{type} view|create|edit|delete` (plus `{type} confirm` for types with an approval step) are generated by `RoleSeeder`. It is idempotent; when it changes, add a migration that runs it so existing databases get the permissions (see `*_sync_roles_and_permissions.php`).
- **Frontend:** state file in `resources/js/components/store/state/` (endpoints), a key in `utils/constants.jsx` `stateKey`, registered in `global-slice.jsx` `INITIAL_STATE`; a page built on `shared/misc/DataTable.jsx`; a route in `app.jsx` with its permission; a menu item in `shared/layout/Header.jsx` behind the same permission.

Kiosk actions that students do without logging in (check-in/out, booking, counsel submit, loan request) have their own controllers and routes (`BookingController`, `CheckinController`, `CounselController`, `EquipmentLoanController`). Domain rules shared by the kiosk and admin paths live in a service (e.g. `EquipmentLoanService`), never duplicated in two controllers.

Follow the existing module that is closest (bookings for anything with an approval flow, facilities for parent/child data) before inventing a structure.

## Security rules

- Only the types in `config('constants.PUBLIC_MASTER_TYPES')` can be listed without logging in (what the kiosk needs). Every other type's `index`/`show` requires login plus `{type} view`, enforced in the `MasterApiController` constructor. Add a type to the public list only if the kiosk needs it and it holds no personal data.
- Public `bookings` and `checkin` lists leave out the `student` relation for guests (only `student_id`). Keep it that way when changing those queries.
- Kiosk cancel endpoints require the matching `student_id` unless the caller is staff with `{type} edit`; the kiosk sends it.
- **Accepted by design:** students never log in at the kiosk, so the kiosk cannot prove who a student is, and student ids are public. The `student_id` check only stops accidental or blind cancels (plus a rate limit). Do not add student authentication, PINs or cancel tokens, and do not report this as a vulnerability, unless the owner asks for it.
- Don't eager-load full `user` relations into API responses; select only the columns needed (`'user:id,name'`).

## Frontend data layer contract (`store/global-slice.jsx`)

- `getRecords` resolves to an array and never throws. On failure it toasts and keeps the last good data.
- `createRecord` / `updateRecord` / `importRecord` resolve to `true` (or the result with `returnData`) and **throw an `ApiError` on failure**, with `fieldErrors` from Laravel's 422. The kiosk flows in `Home.jsx` rely on the throw to skip their success branch. Never change this to return `false`.
- `deleteRecord` resolves to `true` / `false`.
- The thunks show error toasts themselves. Pages own their list: they format rows, store them with `setStateData`, and refetch after saving. Thunks never write save results into a list.
- Always `await dispatch(createRecord(...))` inside `try/catch` in forms. Without `await`, the result is a Promise and every save looks successful.
- The API base URL is the page's origin and the token is read from the auth cookie on every request (`components/api.jsx`). Don't reintroduce `APP_URL` or effect-based token setup.
- Send calendar dates as local `YYYY-MM-DD` (luxon `toISODate()`), not `toISOString()`, which shifts the day for UTC+7/+8 users.

A planned migration moves all pages to RTK Query in one go. Until then, don't introduce a second data-fetching pattern.

## Kiosk (`components/pages/Home.jsx`)

One Stepper with shared Level → Class → Name steps, then flow-specific panels chosen by `activeButton`. PrimeReact `StepperPanel`s must be direct children of the `Stepper`, so panels stay in `Home.jsx` and their contents live in `components/pages/kiosk/`.

## Behaviour specs

- Equipment loans: `.github/equipment-loan-behavior.md`. Follow it for any loan, CCA or equipment change.

## Tests and data safety

- PHPUnit runs on in-memory SQLite (`phpunit.xml`). Never point tests at MySQL.
- Every bug fix and feature ships with a feature test. Roles and permissions exist in tests because the sync migration runs them.
- Never edit a migration that is part of a tagged release; add a new one.
- Records with history (equipment with loans, CCAs) are deactivated, not deleted.
- Imports never delete existing records. Levels/classes/students are matched by name; activities, support strategies and facilities are updated in place by their key (`MasterApiController::importKeys`). New import types follow the same rule.
- Radio question options are synced in place (`syncRadioOptions`) so answers keep pointing at their option; never delete-and-recreate options.

## Git workflow

- Branch from `develop` as `feat/*`, `fix/*` or `chore/*`; open the PR into `develop` (not `main`, which is the default branch on GitHub). Never commit to `main` or `client/*` directly.
- Conventional Commits (`fix(loans): ...`), with the issue IDs a commit closes in the body (`Closes: C2`).
- Releases: `develop` is fast-forwarded into `main` and tagged `vX.Y.Z`. See README.

# Laravel Boost

## Tools

- Laravel Boost is an MCP server with tools designed specifically for this application. Prefer Boost tools over manual alternatives like shell commands or file reads.
- Use `database-query` to run read-only queries against the database instead of writing raw SQL in tinker.
- Use `database-schema` to inspect table structure before writing migrations or models.
- Use `get-absolute-url` to resolve the correct scheme, domain, and port for project URLs. Always use this before sharing a URL with the user.
- Use `browser-logs` to read browser logs, errors, and exceptions. Only recent logs are useful, ignore old entries.

## Searching Documentation (IMPORTANT)

- Use `search-docs` before changes that depend on Laravel ecosystem APIs, behavior, configuration, or version-specific syntax. Skip it for copy-only edits and other changes where package documentation is irrelevant. Reuse sufficient results already in context instead of searching again.
- Pass a `packages` array to scope results when you know which packages are relevant.
- Use multiple broad, topic-based queries: `['rate limiting', 'routing rate limiting', 'routing']`. Expect the most relevant results first.
- Do not add package names to queries because package info is already shared. Use `test resource table`, not `filament 4 test resource table`.

### Search Syntax

1. Use words for auto-stemmed AND logic: `rate limit` matches both "rate" AND "limit".
2. Use `"quoted phrases"` for exact position matching: `"infinite scroll"` requires adjacent words in order.
3. Combine words and phrases for mixed queries: `middleware "rate limit"`.
4. Use multiple queries for OR logic: `queries=["authentication", "middleware"]`.
